# Supplier module: API documentation and tests

## Swagger UI

Start the application with Docker Compose and open:

- Swagger UI: http://localhost:8000/api/docs
- OpenAPI 3.0 JSON: http://localhost:8000/api/docs.json

Swagger UI is served by Symfony. Its UI assets are loaded from the Swagger UI public CDN; the OpenAPI document itself is generated by the application.

## Test strategy

The backend PHPUnit configuration defines a default suite for CI and five focused suites:

- **Supplier Unit**: domain model validation/normalization and application use cases. The `HandleSupplierEvent` tests cover duplicate delivery, delayed events after deletion, unsupported event types and Elasticsearch failures that must be retried.
- **Supplier Functional**: real Symfony HTTP kernel, routing, JSON payload handling, Doctrine persistence and Oracle database behavior.
- **Supplier Infrastructure**: infrastructure-level components such as event-envelope validation and encryption.
- **Supplier Integration**: a live end-to-end test that requires Oracle, Redis, Elasticsearch, RabbitMQ, the outbox publisher and the Supplier consumer.
- **Observability Unit**: Prometheus metrics formatting and exposition.

Functional tests use a transaction and roll it back after each test. They require Oracle and the ERP_APP schema to be available. Seed at least one purchase order to run the foreign-key deletion test; that test is skipped when there are no purchase orders.

## Run tests

From the repository root:

```bash
docker compose exec backend composer test
docker compose exec backend composer test:unit
docker compose exec backend composer test:functional
```

The default `composer test` command runs the Default suite and does not require the background workers. To run the real event pipeline test, first start the complete stack:

```bash
docker compose up -d --build
docker compose exec backend composer test:integration
```

The integration test creates, updates and deletes a Supplier through the HTTP kernel. It waits for each committed Oracle outbox event to reach `PUBLISHED`, verifies that the RabbitMQ consumer has updated or removed the corresponding Elasticsearch document, and confirms that every event reaches `PROCESSED` in the persistent idempotency ledger. It has a 30-second timeout per asynchronous assertion and uses a unique email address. It deliberately does not wrap the test in a database transaction, so the independent worker processes can see the committed rows.

If the PHPUnit bridge has not downloaded its PHPUnit runner yet, run:

```bash
docker compose exec backend composer install
```

The tests run with APP_ENV=test. The functional suite intentionally uses the configured Oracle connection and does not create or drop schema objects.


## Supplier asynchronous events

Supplier changes are written to the Oracle transactional outbox and published to RabbitMQ. The consumer updates the Elasticsearch read model and invalidates the Redis list cache.

Failed outbox records can be returned to the publisher with:

```bash
docker compose exec backend php bin/console supplier:outbox:retry-failed
```

Messages that exceed the consumer retry limit are routed to the durable `supplier.events.dead` queue. After fixing the underlying issue, replay a bounded number of messages with:

```bash
docker compose exec backend php bin/console supplier:events:dead-letter:replay --limit=100
```

The replay command republishes each message to the main supplier exchange and acknowledges its dead-letter copy only after RabbitMQ confirms the new publication. If publication fails, the original message is requeued in the dead-letter queue. Replayed messages start a fresh consumer retry cycle.

## Outbox concurrency and delivery guarantees

The publisher claims one pending event inside an Oracle transaction with `FOR UPDATE SKIP LOCKED`, marks it as `PROCESSING`, and commits the claim before contacting RabbitMQ. This lets multiple publisher instances work on different rows without waiting on the same locked event.

A claim has a 60-second lease. If a worker exits unexpectedly, a later publisher returns expired `PROCESSING` records to `PENDING`. Successful RabbitMQ publication uses publisher confirms before Oracle is updated to `PUBLISHED`.

This is an **at-least-once** delivery design, not exactly-once delivery. If RabbitMQ confirms a message but the worker crashes before Oracle records `PUBLISHED`, the event can be published again after lease recovery. Consumers must therefore remain idempotent. The Supplier consumer reloads the current Oracle aggregate state before updating Elasticsearch. It also claims each `eventId` in the Oracle `supplier_consumed_events` ledger. A successfully completed event is marked `PROCESSED`; later deliveries of that ID are acknowledged without repeating the read-model operations. A second delivery that encounters a live `PROCESSING` claim is also acknowledged: the original RabbitMQ delivery is still unacknowledged and remains responsible for completion or broker redelivery if its worker disconnects. A failed operation releases its claim back to `PENDING`. Claims use a five-minute lease and a unique claim token, so a worker that lost ownership cannot mark another worker's attempt as complete. This reduces duplicate work but does not make Oracle, Elasticsearch and Redis one distributed transaction: a crash after an external side effect and before the completion update can still cause that idempotent side effect to be repeated.

## Failure-injection and recovery runbook

Run these checks only against a disposable development/test stack. Do not stop shared production dependencies or replay the production dead-letter queue as an experiment.

### 1. RabbitMQ unavailable during outbox publication

1. Create a test Supplier and record its outbox event ID.
2. Stop RabbitMQ briefly:
   ```bash
   docker compose stop rabbitmq
   docker compose exec backend php bin/console supplier:outbox:publish --limit=10
   ```
3. Inspect the outbox row in Oracle. The publisher must not mark the event `PUBLISHED` when it cannot obtain a broker confirm. It records a failed attempt and schedules a retry (or marks it `FAILED` after the configured attempt limit).
4. Restore RabbitMQ and run the publisher again:
   ```bash
   docker compose start rabbitmq
   docker compose exec backend php bin/console supplier:outbox:publish --limit=10
   ```

Expected guarantee: no successful broker confirm means no `PUBLISHED` transition.

### 2. Crash after broker confirm, before the Oracle status update

This is the unavoidable duplicate-delivery window in the outbox publisher:

1. Use a disposable stack and create a test Supplier.
2. Start one publisher process and terminate it forcibly at the narrow point after RabbitMQ confirms publication but before the Oracle `PUBLISHED` update. This requires a debugger/fault-injection breakpoint in the publisher; simply killing an arbitrary process is not deterministic.
3. Confirm the row remains `PROCESSING` until its 60-second lease expires.
4. Run the publisher after the lease expires. The event becomes eligible again and may be published a second time.
5. Confirm the consumer converges Elasticsearch to the current Oracle Supplier state and does not create duplicate logical documents.

Expected guarantee: at-least-once delivery. A duplicate publication is possible and is not a defect; consumers must be idempotent. Do not describe this as exactly-once delivery.

### 3. Dead-letter replay while RabbitMQ is unavailable

1. Put a disposable test message in `supplier.events.dead` (or cause a test event to exhaust its consumer retries).
2. Stop RabbitMQ and invoke the replay command. The command must fail to connect; it cannot acknowledge or remove the original dead-letter message.
3. Start RabbitMQ and inspect the DLQ depth:
   ```bash
   docker compose exec rabbitmq rabbitmqctl -p /erp list_queues name messages
   ```
4. Replay a bounded number of messages:
   ```bash
   docker compose exec backend php bin/console supplier:events:dead-letter:replay --limit=10
   ```

Expected guarantee: replay acknowledges a dead-letter copy only after the main-exchange publish receives a broker confirm. If publish fails after the message has been fetched, the code negatively acknowledges it with requeue.

### Inspect outbox state

```sql
SELECT event_id, event_type, status, attempts, locked_until, last_error
FROM supplier_outbox_events
ORDER BY occurred_at DESC
FETCH FIRST 30 ROWS ONLY;
```

These are operational fault-injection procedures, not automated PHPUnit tests. The live pipeline test covers the normal create/update/delete path; the failure windows above require controlled broker/process fault injection to test deterministically.

Apply the consumer idempotency ledger to an existing Oracle schema:

```bash
docker compose exec -T oracle bash -lc 'sqlplus "$APP_USER/$APP_USER_PASSWORD@//localhost:1521/FREEPDB1"' < database/oracle/010_create_supplier_consumed_events.sql
```

Inspect recent consumer state and recovery leases:

```sql
SELECT event_id, event_type, aggregate_id, status, attempts, locked_until, processed_at, last_error
FROM supplier_consumed_events
ORDER BY received_at DESC
FETCH FIRST 30 ROWS ONLY;
```

## Supplier event metrics and alerts

The backend `/metrics` endpoint exposes shared Supplier worker metrics stored in Redis. The publisher and consumer update the same Redis keys even though they run in separate processes.

Important Prometheus metrics:

- `erp_supplier_events_published_total`
- `erp_supplier_events_consumed_total`
- `erp_supplier_events_deduplicated_total`
- `erp_supplier_events_failed_total`
- `erp_supplier_events_dead_letter_total`
- `erp_supplier_outbox_pending_events`
- `erp_supplier_outbox_failed_events`
- `erp_supplier_outbox_oldest_pending_age_seconds`

The Grafana dashboard `ERP Procurement - Overview` includes Supplier event throughput and outbox health panels. Prometheus alerts cover a growing pending backlog, old pending events, failed outbox records and dead-lettered messages.

Check the endpoint locally:

```bash
curl http://localhost:8000/metrics | grep erp_supplier
```

Run the focused test suites:

```bash
docker compose exec backend composer test
docker compose exec backend vendor/bin/simple-phpunit --testsuite="Supplier Infrastructure"
docker compose exec backend composer test:integration
docker compose exec backend vendor/bin/simple-phpunit --testsuite="Observability Unit"
```
